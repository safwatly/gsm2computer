# Call cut at 17:43 UTC, 2026-10-17

Diagnosis and proposed repair only. No runtime changes are included. Base and
live hub source: `a6f3669`, branch `feat/portal-rich-with-sim`. The live copies of
`hub.py`, `call_link.py`, `link_gap_log.py`, and `ws_backpressure.py` are byte-for-byte
identical to this checkout.

## Finding and confidence

The call's phone-to-hub TCP path stalled and then reset. The decisive recovery
bug in the repository is that the Android client **never reconnects**: it converts
a WebSocket failure into GSM teardown. The server's 65-second grace window can
accept a replacement connection, but cannot cause the phone to create one.

This is a confirmed source-code defect and is consistent with the incident.
The installed APK revision could not be verified: ADB listed the Pixel as a
connected device, but a single 15-second bounded `adb shell logcat` attempt timed
out with zero output. No ADB retry, reconnect, or daemon restart was attempted.
Consequently the exact phone exception, GSM disconnect time, and origin of the
TCP reset remain unconfirmed. Tailscale reachability alone does not establish
application or ADB responsiveness.

## Why the phone did not relink

1. `HubStreamClient.start()` launches `connect()` once. No reconnect scheduler,
   retry loop, network callback, or second `newWebSocket()` path exists.
2. `HubStreamClient.onFailure()` calls `sink.onError()` immediately.
   `onClosed()` also reports a fatal error unless locally stopped. `sendAudio()`
   ignores the boolean return from `WebSocket.send()`.
3. `RtpSession.transportSink.onError()` invokes `onRtpTimeout()`.
4. `CallOrchestrator.onRtpTimeout()` calls `tearDown("Hub stream timeout")`, which
   stops the session/transport and disconnects the active GSM call. Later
   Tailscale recovery cannot revive that call.
5. The phone ignores `session.id` in `session.updated` and sends no resume header.
   The hub already supports a header-less reconnect during an active grace wait,
   so a missing header alone would not explain this incident. The missing
   reconnect attempt and fatal error policy do.
6. `RelinkGate` merely waits for an incoming replacement. `_hold_for_relink()`
   detaches the failed downlink and waits without a second call-slot claim.
   `link_gap_log.py` records events; it has no reconnect mechanism.

A silent phone process stall would also prevent a reconnect. The failed ADB
attempt prevents ruling that out for this particular incident. Clean scheduled
e2e closures test normal shutdown, not Android failure recovery over LTE.

## Could backlog handling starve the socket?

There are two different mechanisms:

- **Hub event loop/read starvation:** `_pump_out()` yields at its 20 ms source
  reads, admits a bounded transport backlog, and drops excess frames. It never
  awaits the WebSocket writer's drain. Ping/pong writes also do not await drain.
  Repeated backlog warnings and five-second path probes continued through the
  failure. There is no evidence the downlink guard blocked the reader/event loop.
  This does not rule out every source of read delay: the separate uplink
  `write_in()` awaits the playback pipe's drain inline in the WebSocket reader.
  No incident evidence establishes a stall there.
- **TCP head-of-line delay:** the backlog cap measures only the asyncio transport,
  not the kernel send queue or unacknowledged TCP bytes. Dropping a new frame
  cannot discard old audio already queued to TCP. WebSocket pongs share the same
  ordered byte stream and cannot overtake audio. Thus prolonged network or peer
  read stalls can delay pongs despite the nonblocking hub implementation. The
  phone's 20-second OkHttp ping interval can then turn a stall into a fatal
  transport failure. This is a plausible reset mechanism, not a verified logcat
  finding. Increasing grace or disabling pings does not fix the missing retry.

At 48 kHz mono PCM, base64 alone costs 128,000 bytes/s (1.024 Mbit/s) in each
direction before JSON, TCP and tunnel overhead. Continuous audio, including
silence, makes this path more sensitive to variable LTE capacity. No codec or
audio routing change is justified solely by the current evidence.

## Proposed repair for a separate implementation PR

Prioritize a bounded, same-call Android reconnect state machine:

1. Cache the hub-issued `session.id` after initial establishment. Only recover a
   hub-owned established session; do not apply this policy to the direct OpenAI
   path or blindly create a fresh session when the old identity is unknown.
2. On transient reset/EOF/ping failure, enter `RECONNECTING` and report status
   instead of `Sink.onError()`. Retain the GSM leg and existing audio session;
   discard unsent media during the gap. Cancel the failed socket so old queued
   audio cannot replay. Flush stale local playback before resuming.
3. Retry with a monotonic deadline below the hub's 65-second grace (for example,
   a 55-second phone budget with 0.25/0.5/1/2-second capped backoff). Bound token
   HTTP calls and connection establishment by the remaining budget. The current
   zero read timeout also applies to token HTTP requests and must be separated
   from WebSocket timeout settings. Stop retrying if GSM ends or the user stops.
4. Send `X-Gsm-Call-Session` and require acknowledgement of the same session.
   Scope callbacks by connection generation so late failures cannot tear down a
   replacement. Serialize stop/retry transitions and cancel pending work on stop.
5. Preserve the one-call rule. A resume header must never fall through into new
   session admission after its grace waiter has expired; the current hub can do
   that when idle, so add explicit stale-resume rejection. Handle a short 409
   race while the original socket is transitioning into grace. Do not force
   release, supersede a healthy call, or silently start another Talk session.
6. Keep clean peer 1000/1001 closure and explicit hub termination terminal.
   Only report fatal `onError()` after terminal rejection or exhausted recovery.
   Do not remove existing GSM teardown for genuinely terminal failures.
7. Log attempt number, elapsed time, exception class, HTTP status, session ID,
   generation and terminal reason. Never log credentials or connection URLs.

For backpressure, first add per-call socket telemetry (exact local/remote tuple,
Send-Q, bytes not sent, retransmissions and TCP window) plus phone send-queue and
ping-failure diagnostics. Then evaluate a bounded kernel send buffer and lower
wire bitrate on an isolated test device. Do not attempt to prioritize pongs by
interleaving bytes inside already-written WebSocket frames or drop arbitrary
bytes from a TCP stream. A larger grace period alone leaves both failure modes.

## Validation and limits

23 existing offline tests passed against the checkout's `call_link.py`,
`call_slot.py`, and `ws_backpressure.py`: close classification, path parsing,
same-session/header-less gate behavior, grace handling, frame admission,
transient stall recovery and dead-socket policy. Test files were reused from the
live installation; test objects were isolated and never attached to the running
hub. The hub process was not imported or controlled.

A future code change needs deterministic Android transport tests covering reset
then same-session recovery, ping timeout, repeated token/connect failure,
stop/GSM-end during backoff, late callbacks, stale resume rejection, clean close,
and deadline exhaustion. Fault injection and APK identification should happen
on an isolated test device before any separately authorized deployment. No live
calls, e2e calls, deployment, restart, SMS, or call-slot operation was performed
for this diagnosis.
